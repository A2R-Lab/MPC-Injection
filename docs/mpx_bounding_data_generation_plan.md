# Fixed-Speed MPX Bounding-Data Plan

Status: final implementation plan

## Objective

Produce a validated nominal-dynamics dataset of complete Unitree Go2 trajectories
generated by MPX from the simulator's initial reset state through immediate
acceleration, gait onset, and sustained bounding at a commanded forward velocity
of `0.5 m/s`. Once bounding begins, measured foot contacts must show a symmetric
bound: the front legs act as a pair, the rear legs act as a pair, and front/rear
support alternates.

This plan ends when the accepted trajectory files, attempt manifest, validation
summary, and checksums exist. Loading the data into a replay buffer, training a
policy, domain randomization, and evaluating a learned policy are explicitly
deferred.

## Verified starting point

- The accepted opt-in action interface is `mpx_bound_scale_1_no_lpf_v1`: 12D,
  scale 1.0, no action LPF, with
  `q_target = q_des + tau_ff / kp_realized`. Rollouts advance through
  `env.step(raw_action)`.
- Saved-action transition parity passed under the predeclared nominal and
  deterministic-DR checks in
  `mpx_bound_milestone_reports/transition_parity_env_step_scale1_no_lpf_report_v3.json`.
- The strongest recorded bounding candidate is not an in-place bound. It is
  `bound_front_first`, duty factor 0.5, 3 Hz, 0.03 m step height at a commanded
  `0.1 m/s`.
- A direct-torque 10-second run at `0.1 m/s` completed without a safety reset and
  showed front-pair and rear-pair support. A 60-second run had three resets.
  Recorded `0.2 m/s` and `0.3 m/s` trials also reset.
- The later environment-step diagnostic at `0.1 m/s` completed 150 control steps
  without a fall or non-foot contact. Measured pair agreement was 0.9617 front
  and 0.9733 rear, but all-four support occupied 60.5% of substeps, no flight was
  measured, 1.1667% of action elements clipped, and 0.6528% of requested torque
  elements saturated.
- No recorded run establishes bounding in place or at `0.5 m/s`. Both the
  interactive controller and the dataset generator change the controller duty
  factor to 1.0 below a 0.05 command threshold, so zero command currently means
  standing rather than bounding in place.
- `generate_trajectory()` accepts an internal fixed command and can save the
  required environment-step diagnostics. The batch wrapper and CLI do not expose
  the fixed command or gait settings and currently accept a trajectory based only
  on fall/completion status.
- The copied original trot file
  `data/quadruped_dr/sysid_dyn20_mjlab_10k/quadruped_dr_sysid_dyn20_mjlab_seed_000016_ep_1000.npz`
  contains 1,000 control transitions at 50 Hz and spans 20 seconds. The three
  copied shard manifests contain 8,937 accepted attempts, but they do not prove
  the complete original 10,000-file set is present locally.

Consequently, the retained 0.1 m/s settings are only a starting point for a
0.5 m/s commissioning run. They are not an accepted production configuration.

## Frozen scope decisions

Measured flight is not required. Accepted trajectories must instead show
repeated measured front-pair/rear-pair alternation; brief all-four support is
allowed between paired support intervals. Every accepted file begins at the
simulator's initial reset state and immediately starts the acceleration ramp;
there is no standing hold. It includes the ramp, gait onset, and sustained
target-speed phases. The applied command schedule must be saved exactly and must
reach and hold `[0.5, 0.0, 0.0]`; dataset inclusion does not depend on an achieved-velocity
threshold. Overall and per-gait-cycle achieved body-frame velocity must still be
measured and reported when choosing and evaluating the controller configuration.
The command schedule uses 50 ramp transitions at 50 Hz with forward commands
`0.01, 0.02, ..., 0.50 m/s`, followed by 950 transitions holding 0.5 m/s.
Each accepted trajectory therefore matches the original trotting trajectory
length: 1,000 control steps over 20 seconds. The final target is 10,000 accepted
trajectories, gated by a fully validated 100-trajectory pilot. Commissioning starts with
`bound_front_first` but may select `bound_hind_first`. It may tune gait
parameters, MPX cost/reference parameters, and joint feedback gains when
supported by measured failures. Nominal plant dynamics, actuator limits, safety
contact/fall detection logic, and `mpx_bound_scale_1_no_lpf_v1` remain fixed.
Pitch and minimum-height termination thresholds start at their environment
defaults and may change only through the evidence-based pre-pilot process below.

Nominal generation retains the environment's seeded reset variation in joint
positions, base roll/pitch, and joint velocities. This initial-state diversity
is not domain randomization: masses, friction, joint dynamics, gains, actuator
strength, and other plant properties remain fixed.

## Implementation sequence

### 0. Freeze and commit the starting point

- Commit the finalized plan before making implementation changes. The existing
  action-interface and parity work is already committed at `abd1a4d7`.
- Confirm the committed worktree and submodule revisions before commissioning.
- Give every subsequent smoke, calibration, pilot, and production attempt an
  explicit `passed` or `failed` result with the reason and measured evidence.
- Commit each completed, validated implementation milestone before starting the
  next materially different stage. Do not commit generated bulk trajectory
  files unless explicitly requested.

### 1. Make the canonical generator select the requested experiment

Extend `mpc_rl/planner/gen_traj_data_mpx_dr.py` rather than creating another
rollout implementation.

- Add batch-function and CLI inputs for a target three-element command, command
  ramp, gait, duty factor, step frequency, and step height.
- Construct the shared `MPCControllerWrapper` with those instance-owned gait
  settings and planned-contact diagnostics enabled.
- Apply the same deterministic ramp/hold command schedule in every batch
  attempt; do not resample it.
- Use `domain_rand_config_type=disabled` and
  `action_interface_id=mpx_bound_scale_1_no_lpf_v1` for this dataset.
- Preserve the selected moving duty factor rather than hard-coding 0.5 when the
  command is nonzero.
- Record every applied command plus the effective schedule, gait, action
  interface, controller settings, and nominal-dynamics selection in every file
  and manifest record.
- Include the gait and fixed speed in output filenames so unrelated data cannot
  be mixed accidentally.

Add focused tests for argument validation, controller construction, command
schedule propagation, shared-controller reset behavior, metadata, filenames,
and unchanged legacy defaults.

### 2. Reproduce the known narrow candidate through the canonical path

Run one short nominal rollout at `0.1 m/s` using the retained gait settings and
the accepted environment-step action interface. This is a plumbing regression
check, not part of the requested dataset and not an invitation to calibrate other
speeds.

Compare its completion, measured contact pattern, clipping, saturation, posture,
and velocity statistics with the existing diagnostic. Stop and diagnose any
material regression before attempting `0.5 m/s`.

### 3. Commission only the target speed

Run a short nominal smoke trajectory from the initial reset state through the
configured command ramp and into sustained `0.5 m/s` operation using the retained
configuration:

- `bound_front_first`
- duty factor 0.5
- 3 Hz
- 0.03 m step height
- target command `[0.5, 0.0, 0.0]` after the one-second ramp
- `mpx_bound_scale_1_no_lpf_v1`
- nominal dynamics with the repository Go2 sysID model enabled

Inspect measured substep contacts rather than accepting the planned schedule as
proof. Also inspect forward tracking, base height, roll/pitch, action clipping,
torque saturation, solver finiteness, falls, and all non-foot contacts.

If the retained `bound_front_first` phase orientation is inferior at 0.5 m/s,
commissioning may switch to `bound_hind_first`. The chosen orientation must be
frozen before the 100-trajectory pilot; production files must not mix phase
orientations.

If this succeeds, freeze the exact configuration and acceptance thresholds. If
it fails, retain every failed report and tune the smallest relevant MPX surface.
Change one parameter group at a time in this order:

1. step frequency and step height;
2. duty factor; measured flight remains optional;
3. MPX reference/cost parameters that directly oppose sagittal bounding;
4. joint feedback gains only if the failure evidence implicates tracking rather
   than the planned motion.

Do not increase actuator limits, weaken fall/non-foot checks, change the accepted
action interface, introduce domain randomization, or explore speeds other than
the 0.1 m/s regression check and the 0.5 m/s target.

Before freezing the pilot configuration, render and visually inspect at least
one automated-validator-passing 0.5 m/s trajectory. Record the visual result and
any visible pitching, dragging, scuffing, or anomalous impacts. Visual inspection
cannot override a failed measured-contact, safety, or replay check.

### 4. Freeze an operational acceptance predicate

Separate commissioning attempts from production seeds. Freeze thresholds before
examining production attempts.

Every accepted trajectory must satisfy these invariant checks:

- the saved per-step commands exactly match the configured ramp/hold schedule,
  which starts at the initial state, reaches `[0.5, 0.0, 0.0]`, and sustains it;
- requested horizon completes without termination, truncation, fall, torso
  contact, or any other non-foot ground contact at any simulation substep;
- all required arrays and scalar metadata exist, shapes agree, and numeric data
  are finite;
- saved actions are in `[-1, 1]` and action-interface metadata exactly matches
  `mpx_bound_scale_1_no_lpf_v1`;
- replaying all saved actions from the saved initial state reproduces qpos, qvel,
  observations, rewards, discrete outcomes, applied torques, and contact/push
  diagnostics within the already accepted parity tolerances;
- fewer than 1% of action elements are clipped in each accepted trajectory;
  raw actions, clipping masks/magnitudes, and per-joint clipping rates remain
  fully reported;
- maximum normalized clipping magnitude is initially 0.1 (raw actions within
  `[-1.1, 1.1]`). If otherwise successful 0.5 m/s bounding remains blocked after
  the allowed controller tuning is exhausted, this magnitude may be revised as
  an explicit last-ditch decision. Any revision must be justified by failed
  evidence and frozen in a new versioned acceptance declaration before the
  100-trajectory pilot; it cannot be selected after inspecting pilot or
  production results;
- torque saturation does not reject an otherwise accepted trajectory. Requested
  and applied torques, saturation masks/fractions, and overshoot magnitudes must
  still be retained and summarized so controller quality remains visible;
- posture initially satisfies the environment defaults (`abs(pitch) <= 0.5 rad`,
  `abs(roll) <= 0.5 rad`, and base height `>= 0.1 m`). If an otherwise clean
  measured bound is blocked specifically by pitch or height, commissioning may
  relax the implicated threshold based on recorded evidence. Revised values must
  be frozen before the 100-trajectory pilot. Roll/pitch/height extrema remain
  reported, and non-foot contact remains an unconditional rejection. Achieved
  velocity tracking is reported as a controller-quality metric rather than used
  to reject a file.

The measured-contact classifier operates on the 19-second hold after the ramp;
the ramp is still covered by all safety, schema, finiteness, action, and replay
checks. Within that target-speed window, it accepts a contact-state change only
after the state persists for two consecutive 200 Hz simulation substeps (10 ms),
then requires:

- at least 80% front-pair agreement (`FL == FR`) and at least 80% rear-pair
  agreement (`RL == RR`) over target-speed simulation substeps;
- at least 10 complete front/rear cycles;
- at least 5% front-only support and at least 5% rear-only support;
- after contact debouncing, at least 80% of consecutive paired-support intervals
  alternate between front-only and rear-only;
- diagonal-only plus lateral-only support occupies no more than 10% of
  target-speed simulation substeps;
- measured flight may occur but is not required.

Planned contacts are diagnostic evidence only; they cannot make a measured-contact
failure pass.

### 5. Generate accepted nominal data

- Use `data/quadruped_bound/nominal_vx0p5/` with separate `commissioning/`,
  `pilot/`, and `production/` directories. Do not mix artifacts across stages.
- First generate and fully validate a 100-trajectory pilot. Do not begin the
  remaining production run unless the pilot passes every frozen acceptance rule.
- Count those 100 pilot files toward the final 10,000 only if the controller
  configuration and acceptance declaration remain unchanged. Any change after
  pilot inspection makes those files commissioning data and requires a new
  100-trajectory pilot.
- After pilot acceptance, continue to a final total of 10,000 accepted
  20-second trajectories.
- Generate attempts from a production seed range disjoint from commissioning.
- Reject failed, unsafe, non-bounding, out-of-tolerance, or replay-divergent
  attempts; never save them as accepted data.
- Preserve a JSONL record for every attempt with its seed, exact configuration,
  failure reason, gait metrics, tracking, posture, clipping, saturation, and
  output filename when accepted.
- Write accepted files through a staging path, validate them, then promote them
  into the final dataset directory.
- Do not start multiple workers until a single-worker accepted file passes full
  validation and deterministic regeneration.
- Keep bulk `.npz` files and large attempt manifests out of Git. Commit only
  code, configuration/declarations, documentation, and compact validation
  reports unless the user explicitly requests otherwise.

### 6. Validate and close the data-generation milestone

Extend the existing integrity/replay tooling rather than adding a disconnected
checker. Validate every accepted file with `allow_pickle=False` and produce:

- a per-file validation result;
- a dataset summary with attempted/accepted/rejected counts and rejection reasons;
- aggregate contact, tracking, posture, clipping, saturation, and solver metrics;
- a SHA-256 checksum index covering every accepted file;
- the exact repository and submodule commits plus normalized generator settings.

Regenerate at least one accepted seed and require identical transition arrays and
metadata except explicitly excluded wall-clock timing fields.

Forward-velocity tracking reports must cover the 19-second hold and include, per
file and in aggregate, mean achieved velocity, signed bias from 0.5 m/s, MAE,
RMSE, 5th/95th percentiles, and per-gait-cycle mean velocity. These are
controller-quality metrics, not file-rejection thresholds. Also report lateral
velocity and displacement plus yaw-rate error and accumulated yaw drift. These
remain non-rejecting metrics unless the trajectory violates a frozen safety or
contact rule.

## Definition of done

This milestone is complete only when:

1. 10,000 nominal MPX trajectories of 1,000 transitions each have been accepted
   with the frozen ramp followed by the `0.5 m/s` target hold;
2. every accepted trajectory passes the frozen measured-bound, safety, schema,
   finiteness, action-interface, and saved-action replay checks;
3. manifests, aggregate validation results, provenance, and checksums are saved;
4. no training or policy-performance claim is included in the result.

## Deferred work

- loading or injecting the dataset for reinforcement learning;
- reward design and bounding-retention training tests;
- domain-randomized or multi-speed generation;
- learned-policy evaluation;
- production artifact publication or real-robot deployment.

## Canonical command-line implementation

The canonical implementation remains
`mpc_rl/planner/gen_traj_data_mpx_dr.py`. Fixed-command runs are opt-in, so
invocations that omit the new command, gait, and acceptance options retain the
legacy sampled-command defaults, filenames, action interface, and DR preset.

An unfrozen commissioning attempt uses the plan thresholds directly and writes
all generated artifacts under the stage directory:

```bash
PYTHONPATH="$PWD/deps/mpx:$PWD/deps/gym-quadruped:$PWD" \
conda run --no-capture-output -n mpc-rl \
python -m mpc_rl.planner.gen_traj_data_mpx_dr \
  --num-trajectories 1 \
  --episode-length 1000 \
  --start-seed 1000 \
  --max-attempts 1 \
  --output-dir data/quadruped_bound/nominal_vx0p5/commissioning \
  --target-command 0.5 0 0 \
  --command-ramp-control-steps 50 \
  --gait bound_front_first \
  --duty-factor 0.5 \
  --step-frequency-hz 3 \
  --step-height-m 0.03 \
  --commissioning-acceptance \
  --stage commissioning
```

The commissioning flag is deliberately invalid for pilot or production. Those
stages require `--acceptance-declaration <path>` referencing a frozen JSON
declaration. The generator validates the declaration, forces nominal dynamics,
the accepted action interface, the declared command schedule and gait, writes a
candidate through `.staging/`, loads it with `allow_pickle=False`, replays every
saved action, and promotes it only after all checks pass. The first accepted
seed is regenerated and compared exactly before the run continues.

Commissioning-only controller studies can record instance-local MPX pitch,
pitch-rate, body/foot vertical tracking, and body-height reference overrides with
`--mpx-qrot-pitch-cost`, `--mpx-qomega-pitch-cost`,
`--mpx-qp-height-cost`, `--mpx-qdp-vertical-cost`, and
`--mpx-qleg-vertical-cost`, `--mpx-robot-height-m`, or
`--mpx-swing-clearance-speed-m-per-s`. Joint feedback studies can
use scalar `--joint-kp` and `--joint-kd` values or explicit hip/thigh/calf triplets through
`--joint-kp-by-type` and `--joint-kd-by-type`. These values are serialized in
the acceptance declaration and realized controller metadata; a frozen
declaration reconstructs them for pilot and production instead of relying on
process-global MPX configuration mutation.

Seed namespaces are enforced as disjoint ranges: commissioning uses
`0..99,999`, pilot uses `100,000..199,999`, and production begins at `200,000`.

Each stage directory contains `generation_manifest.jsonl` with one explicit
passed/failed record per attempt, `validation_results.jsonl` with per-file
integrity and replay results, `validation_summary.json` with aggregate metrics
and provenance, and `checksums.sha256.json`. Trajectory filenames encode the
gait, fixed command, seed, and horizon. These generated files remain excluded
from Git by the repository's `*.npz` rule; bulk JSONL artifacts must likewise
remain uncommitted.
